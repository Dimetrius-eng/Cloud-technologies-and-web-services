**2.1. Що таке віртуальна машина та які особливості їх реалізації у Azure Virtual Machine?**<br>

**Віртуальна машина (Virtual Machine, VM)** — це програмно емульований комп'ютерний комплекс, який функціонує на базі фізичного серверного обладнання під контролем гіпервізора, 
маючи виділені віртуальні процесори (vCPU), оперативну пам'ять, віртуальні накопичувачі та мережеві інтерфейси. Вона реалізує модель обслуговування **IaaS (Infrastructure as a Service)**, 
надаючи користувачеві повний адміністративний контроль над гостьовою операційною системою (Linux або Windows) та встановленим стеком ПЗ.

**Ключові особливості реалізації віртуальних машин у Microsoft Azure (Azure VM):**
1. **Гіпервізорна база:** Інфраструктура Azure базується на кастомізованій платформі віртуалізації Microsoft Hyper-V та передовій архітектурній системі апаратного розвантаження Azure Boost 
(що забезпечує ізоляцію мережевих операцій і дискового вводу-виводу на виділених платах прискорення).
2. **Розгалужена сітка серій (VM Sizes):** Інстанси розділені за спеціалізованими категоріями:
   * *General Purpose (B, D-серії):* збалансоване співвідношення процесора та пам'яті (B-серія підтримує технологію накопичення кредитів Burstable для непостійних навантажень);
   * *Compute Optimized (F-серія):* високопродуктивні процесори для обчислювальних алгоритмів та веб-серверів;
   * *Memory Optimized (E, M-серії):* значний обсяг оперативної пам'яті для кешуючих систем та реляційних баз даних (SAP HANA, SQL Server);
   * *GPU/Accelerated (NC, NV, ND-серії):* графічні прискорювачі NVIDIA для ШІ, навчання LLM та візуалізації.
3. **Механізми високої доступності:** Підтримка **Availability Zones (Зон доступності)** у межах регіону для досягнення SLA до 99.99%, а також груп доступності **Availability Sets** 
(розподіл за доменами відмов Fault Domains та доменами оновлень Update Domains).
4. **Масштабування:** Сервіс **Virtual Machine Scale Sets (VMSS)** дозволяє автоматично створювати й балансувати пули ідентичних віртуальних машин на основі правил моніторингу навантаження CPU чи мережі.
5. **Інтеграція дисків та мереж:** Використання керованих дисків **Azure Managed Disks** (Ultra Disk, Premium SSD v2, Standard SSD/HDD) та віртуальних мереж **Azure Virtual Network (VNet)** 
із групами мережевої безпеки (Network Security Groups, NSG).

**2.2. Які можливості надає Azure App Service?**

**Azure App Service** — це повнофункціональна керована платформа **PaaS (Platform as a Service)** для швидкого створення, розгортання та масштабування корпоративних веб-додатків, мобільних бекендів та 
RESTful API без необхідності ручного конфігурування операційних систем чи веб-серверів (IIS, Nginx, Apache).

**Основні функціональні можливості Azure App Service:**
* **Багатомовна підтримка середовищ виконання:** Нативна підтримка платформ .NET, .NET Core, Java, Node.js, Python, PHP, а також можливість запуску кастомних Docker-контейнерів у середовищі Windows або Linux.
* **Автоматичне масштабування (Autoscaling):** Динамічне вертикальне (зміна тарифного плану App Service Plan) та горизонтальне масштабування (автоматичне додавання нових інстансів веб-додатка від 1 до 30+ при
зростанні черги HTTP-запитів або споживання пам'яті).
* **Вбудовані засоби безпеки та автентифікації (Easy Auth):** Інтеграція автентифікації користувачів без написання коду через провайдери Microsoft Entra ID (Azure AD), Google, Facebook, GitHub та Twitter.
* **Підтримка користувацьких доменів та SSL/TLS:** Безкоштовне автоматичне надання та регулярне оновлення керованих сертифікатів безпеки (App Service Managed Certificates).
* **Ізоляція та гібридні з'єднання:** Можливість інтеграції у віртуальну мережу (VNet Integration) та використання середовища високої ізоляції App Service Environment (ASE) для захисту внутрішнього корпоративного трафіку.
* **Діагностика та моніторинг:** Глибока інтеграція зі службою телеметрії **Azure Application Insights** для відстеження часу відгуку сторінок, винятків у коді та завантаження серверів у реальному часі.

**2.3. Які основні кроки створення App Service через портал Azure?**

Створення веб-додатка здійснюється через графічний майстер Azure Portal за такими послідовними етапами:
1. **Ініціалізація майстра:** У верхньому рядку пошуку ввести `App Services`, перейти до сервісу та натиснути кнопку **Create -> Web App**.
2. **Базові налаштування (вкладка Basics):**
   * *Project Details:* Обрати активну підписку (Subscription) та призначити або створити нову групу ресурсів (Resource Group);
   * *Instance Details:* Задати глобально унікальне доменне ім'я додатку (буде доступне як `<app-name>.azurewebsites.net`);
   * *Publish:* Вибрати спосіб публікації — вихідний програмний код (**Code**) чи готовий контейнер (**Container**);
   * *Runtime Stack:* Вказати мову програмування та версію інтерпретатора (наприклад, .NET 8, Node.js 20 LTS, Python 3.11);
   * *Operating System:* Обрати операційну систему середовища хостингу (Linux або Windows);
   * *Region:* Вказати географічний регіон дата-центру (наприклад, West Europe або North Europe).
3. **Вибір плану тарифу (App Service Plan):** Створити або обрати існуючий тарифний план, що визначає обчислювальні потужності (CPU/RAM). Для навчальних цілей зазвичай обирається безкоштовний рівень **Free F1** (1 GB RAM, 60 хв CPU/день) 
або тестовий рівень **Basic B1**.
4. **Конфігурація розгортання (Deployment - опціонально):** Підключення до репозиторію GitHub або Bitbucket для налаштування конвеєра безперервної інтеграції GitHub Actions (CI/CD).
5. **Мережа та моніторинг (Networking & Monitoring):** За потреби увімкнути збір телеметрії за допомогою Application Insights.
6. **Перевірка та створення (Review + Create):** Система проводить автоматичну валідацію введених параметрів, після чого натискається кнопка **Create** і через 1–2 хвилини веб-додаток стає активним за наданою URL-адресою.

**2.4. Які особливості реалізації "Access control (IAM)" в  Azure?**

Управління доступом до ресурсів хмари Azure реалізовано на основі моделі **Azure RBAC (Role-Based Access Control / Керування доступом на основі ролей)**. Вона впроваджена через єдиний шлюз управління Azure Resource Manager (ARM) 
та має наступні фундаментальні характеристики:
1. **Компоненти призначення ролі (Role Assignment):**
   * *Суб'єкт безпеки (Security Principal):* користувач, група користувачів, сервісний обліковий запис (Service Principal) або керована сутність (Managed Identity);
   * *Визначення ролі (Role Definition):* набір дозволених (`Actions`) та заборонених (`NotActions`) операцій над ресурсами;
   * *Область дії (Scope):* рівень ієрархії, на який поширюються повноваження.
2. **Чітка 4-рівнева ієрархія областей дії (Scope Hierarchy):**
   `Management Groups (Групи керування) -> Subscriptions (Підписки) -> Resource Groups (Групи ресурсів) -> Resources (Окремі ресурси)`
   *Принцип спадкування:* права, надані на вищому рівні (наприклад, на рівні групи ресурсів), автоматично успадковуються всіма дочірніми ресурсами всередині цієї групи.
3. **Вбудовані базові ролі (Built-in Roles):**
   * **Owner (Власник):** повний доступ до керування ресурсами, включно з правом призначати ролі іншим особам;
   * **Contributor (Співавтор):** право створювати, змінювати та видаляти будь-які ресурси Azure, але без можливості делегувати доступи іншим;
   * **Reader (Читач):** виключно перегляд стану, конфігурацій та метрик ресурсів без права їх модифікації;
   * *Вузькоспеціалізовані ролі:* наприклад, *Virtual Machine Contributor*, *Storage Blob Data Reader*, *Website Contributor*.

**2.5. Розкрийте використання Deployment slots для управління версіями.**

**Deployment Slots (Слоти розгортання)** — це спеціальні ізольовані живі екземпляри веб-додатка в межах одного плану Azure App Service (доступні в тарифних категоріях Standard, Premium та Isolated), 
кожен із яких має власне унікальне доменне ім'я та мережевий контекст.

**Механізм та переваги використання:**
* **Концепція Staging/Production:** Окрім основного робочого слота (**Production**), створюється додатковий слот (наприклад, **Staging** або **Dev**). Нова версія коду розгортається у слот Staging, 
де інженери можуть безпечно провести тестування, прогрівання кешу та перевірку конфігурацій під реальним навантаженням без ризику впливу на користувачів.
* **Миттєве перемикання (Zero-Downtime Swap):** Операція перемикання слотів (**Slot Swap**) полягає у миттєвій заміні IP-маршрутизації на рівні балансувальника Azure. Код зі слота Staging миттєво стає публічним (Production), 
при цьому підключення клієнтів не перериваються і виключається будь-який час простою (Zero Downtime).
* **Миттєвий відкат змін (Instant Rollback):** Якщо після перемикання у новій версії виявлено критичну помилку, адміністратор може виконати повторний зворотний Swap за кілька секунд, повернувши стабільну попередню збірку користувачам.
* **Тестування на живих даних (Traffic Routing / Testing in Production):** Можливість налаштувати відсотковий розподіл живого веб-трафіку (наприклад, направляти 10% випадкових користувачів на слот з новою версією для A/B тестування).

**2.6. Здійсніть огляд Storage Account та його ключових функцій.**

**Azure Storage Account** — це уніфікований хмарний простір високої доступності для централізованого зберігання об'єктних, файлових, табличних та чергових даних у захищеному сховищі Microsoft із забезпеченням криптографічного шифрування 
у стані спокою (Storage Service Encryption, AES-256).

**Ключові функції та характеристики Storage Account:**
* **Глобальна масштабованість:** Здатність зберігати петабайти інформації з автоматичним розподілом навантаження.
* **Рівні резервування даних (Data Redundancy):**
  * *LRS (Locally Redundant Storage):* трикратне копіювання даних у межах одного фізичного дата-центру (найекономічніший варіант);
  * *ZRS (Zone-Redundant Storage):* синхронна реплікація між трьома ізольованими зонами доступності в межах одного регіону;
  * *GRS (Geo-Redundant Storage):* створення трьох копій у первинному регіоні та асинхронне копіювання ще трьох копій у вторинний географічний регіон за сотні кілометрів (захист від регіональних катастроф).
* **Рівні доступу за температурою даних (Access Tiers):** **Hot** (для часто запитуваних даних), **Cool** (для даних зі зберіганням понад 30 днів), **Cold** (рідко запитувані дані від 90 днів) та **Archive** 
(довготривалі архіви від 180 днів з мінімальною вартістю зберігання).
* **Безпека:** Підтримка ключів облікового запису (Access Keys), тимчасових підписів доступу (Shared Access Signatures, SAS) та гранулярного контролю ролей через Entra ID.

**2.8. Опишіть як працювати з Azure Storage на прикладі використання мови C#.**

Для програмної взаємодії з хмарним сховищем Azure у середовищі .NET використовується офіційний клієнтський NuGet-пакет **`Azure.Storage.Blobs`**.

**Послідовність виконання операцій у коді C#:**
1. **Підключення бібліотеки:** Додавання простору імен `using Azure.Storage.Blobs;` та `using Azure.Storage.Blobs.Models;`.
2. **Ініціалізація клієнта:** Створення екземпляра `BlobServiceClient` за допомогою конфігураційного рядка підключення або захищеного токена безпеки.
3. **Отримання посилання на контейнер:** Створення контейнера, якщо він ще не існує, через метод `GetBlobContainerClient`.
4. **Завантаження файлу:** Отримання клієнта конкретного блоба `GetBlobClient` та виклик асинхронного методу `UploadAsync()`.

**Приклад фрагмента коду на мові C#:**
```csharp
using System;
using System.IO;
using System.Threading.Tasks;
using Azure.Storage.Blobs;

class Program
{
    static async Task Main(string[] args)
    {
        // Отримання рядка підключення з налаштувань середовища
        string connStr = Environment.GetEnvironmentVariable("CUSTOM_AZURE_STORAGE_CONNECTION");
        string containerName = "documents-container";
        string fileName = "report.pdf";
        string localFilePath = @"C:\data\report.pdf";

        // 1. Створення клієнта сервісу сховища
        BlobServiceClient serviceClient = new BlobServiceClient(connStr);

        // 2. Створення або підключення до контейнера
        BlobContainerClient containerClient = serviceClient.GetBlobContainerClient(containerName);
        await containerClient.CreateIfNotExistsAsync();

        // 3. Завантаження локального файлу в хмарний Blob
        BlobClient blobClient = containerClient.GetBlobClient(fileName);
        using FileStream uploadFileStream = File.OpenRead(localFilePath);
        await blobClient.UploadAsync(uploadFileStream, overwrite: true);

        Console.WriteLine($"Файл успішно завантажено в Azure Blob Storage. URI: {blobClient.Uri}");
    }
}
```

**2.9. Що таке Serverless та особливості їх реалізації у Azure Functions.**

**Serverless (Бессерверні обчислення)** — це парадигма хмарної архітектури, у якій розробник зосереджується виключно на написанні бізнес-логіки у вигляді окремих функцій, тоді як хмарний провайдер повністю автоматизує надання серверів, 
оновлення ОС, мережеву ізоляцію, балансування та динамічне виділення ресурсів. Оплата нараховується виключно за мілісекунди фактичного виконання коду (Pay-per-execution), а за відсутності викликів вартість дорівнює нулю.

**Особливості реалізації в сервісі Azure Functions (модель FaaS):**
* **Подійна модель запуску (Triggers):** Функція активується зовнішніми тригерами:
  * *HTTP Trigger:* запуск через виклик веб-запиту REST API;
  * *Blob Trigger:* запуск у момент збереження нового файлу в Azure Blob Storage;
  * *Queue / Service Bus Trigger:* реакція на надходження повідомлення в чергу;
  * *Timer Trigger:* регулярне виконання за розкладом Cron.
* **Декларативні зв'язки (Input/Output Bindings):** Унікальний механізм Azure, що дозволяє отримувати дані на вхід функції та записувати результат у бази даних (Cosmos DB, SQL, Blob) декларативно через конфігурацію, 
без написання коду ініціалізації SDK-клієнтів.
* **Тарифний план Consumption Plan:** Забезпечує миттєве горизонтальне масштабування від 0 до сотень паралельних інстансів та надає безкоштовний ліміт (1 мільйон викликів на місяць).
* **Durable Functions:** Спеціальне розширення для побудови складних довготривалих оркестрацій зі збереженням стану (Stateful Serverless) за шаблонами Chaining, Fan-out/Fan-in або Human Interaction.

**2.10. Поясніть різниця між автентифікацією та авторизацією. Як пов'язані Azure RBAC та Entra ID (Azure AD) з цими поняттями?**

* **Автентифікація (Authentication - AuthN):** Процес **перевірки дійсності особи** (хто ви такий?). Відповідає на запитання: «Чи є цей суб'єкт тим, за кого себе видає?». Здійснюється через введення логіна, перевірку пароля, 
розпізнавання біометрії або валідацію одноразових кодів MFA/TOTP.
* **Авторизація (Authorization - AuthZ):** Процес **перевірки та надання прав** (що вам дозволено робити?). Відповідає на запитання: «Чи має цей автентифікований користувач право доступу до конкретної віртуальної машини, 
бази даних чи файлу?».

**Взаємозв'язок Entra ID (Azure AD) та Azure RBAC у хмарі Microsoft:**
1. **Microsoft Entra ID (раніше Azure Active Directory) відповідає за АВТЕНТИФІКАЦІЮ (AuthN):** Це централізована хмарна служба ідентифікації та керування обліковими записами. Вона перевіряє облікові дані користувачів, 
обробляє двофакторну перевірку (MFA), контролює політики безпеки входу (Conditional Access) та видає зашифрований токен ідентичності (OAuth 2.0 / OpenID Connect).
2. **Azure RBAC відповідає за АВТОРИЗАЦІЮ (AuthZ):** Механізм авторизації перевіряє отриманий від Entra ID токен і, зіставляючи його з призначеними ролями (наприклад, Reader, Contributor) на певному рівні підписки чи ресурсної групи, 
дозволяє або блокує конкретні API-операції в Azure Resource Manager.

  * `az webapp list --output table` — перегляд розгорнутих веб-додатків;
  * `az webapp restart --resource-group MyRG --name MyApp` — перезапуск веб-сервісу.

### Відповіді на контрольні питання

**<span>1. В чому суть TOTP аутентифікації? Наведіть приклади в контексті Microsoft Authenticator та Azure MFA (Multi-Factor Authentication).</span>** <br>
**TOTP (Time-based One-Time Password / Тимчасовий одноразовий пароль)** — це стандартизований криптографічний алгоритм генерації одноразових динамічних паролів (специфікація RFC 6238), що базується на комбінації спільного симетричного секретного ключа (Shared Secret) та поточного квантованого системного часу (Unix Timestamp). Кожен код зазвичай складається з 6 цифр і є валідним протягом суворо обмеженого проміжку часу (за замовчуванням 30 секунд), після чого безповоротно втрачає чинність.

**Контекст Microsoft Authenticator та Azure MFA:**
* **Підтримка стандарту OATH TOTP:** Додаток Microsoft Authenticator працює як генератор часових кодів, що не вимагає постійного інтернет-з'єднання на смартфоні у момент входу. В Entra ID адміністратори також можуть реєструвати фізичні апаратні OATH TOTP-токени (брелоки з екраном) для користувачів із підвищеними вимогами до безпеки.
* **Покращений захист від атак (Number Matching):** Традиційні пуш-сповіщення були вразливими до атак втоми від сповіщень (**MFA Fatigue / MFA Bombing**), коли зловмисник масово надсилав запити, сподіваючись на випадкове схвалення користувачем. В Azure MFA реалізовано технологію **Number Matching (Зіставлення чисел)**: на екрані комп'ютера виводиться двозначне число, яке користувач зобов'язаний вручну ввести у додатку Microsoft Authenticator на телефоні, що гарантує фізичну присутність користувача перед екраном ініціатора сесії.
* **Контекстні дані безпеки:** Під час запиту на підтвердження Microsoft Authenticator додатково відображає геолокацію входу за IP-адресою та назву програми, що запитує доступ, підвищуючи безпекову обізнаність користувача.

**<span>2. Опишіть формат JSON: де він використовується, які його особливості. Чи застосовується цей формат у Azure?</span>** <br>
**JSON (JavaScript Object Notation)** — це відкритий текстовий формат представлення та серіалізації структурованих даних, заснований на синтаксисі об'єктів мови JavaScript, але повністю незалежний від конкретних мов програмування. Він використовує дві універсальні структури: колекції пар «ключ: значення» (об'єкти, що позначаються фігурними дужками `{}`) та впорядковані списки значень (масиви, що позначаються квадратними дужками `[]`).

**Ключові особливості формату:**
* Простота синтаксису, легкість візуального сприйняття людиною та компактність порівняно з XML;
* Нативна підтримка високошвидкісного синтаксичного аналізу (парсингу) всіма сучасними мовами програмування;
* Відсутність обов'язкової жорсткої схеми даних, що забезпечує гнучкість при передачі слабоструктурованих об'єктів.

**Застосування формату JSON у хмарній екосистемі Azure:**
У платформі Microsoft Azure формат JSON є основним системним стандартом:
1. **Azure Resource Manager Templates (ARM-шаблони):** Декларативний опис хмарної інфраструктури за методологією Infrastructure as Code (IaC) створюється у вигляді JSON-файлів, що описують конфігурацію, параметри та залежності всіх створюваних ресурсів.
2. **Конфігураційні файли додатків:** Налаштування середовища у сервісах Azure Functions (`host.json`, `local.settings.json`) та Azure App Service використовують JSON.
3. **Обмін даними через Azure REST API:** Усі відповіді та запити між клієнтом (браузер, CLI, SDK) та платформою Azure Control Plane передаються у форматі JSON.
4. **Вивід утиліти Azure CLI:** За замовчуванням усі команди командного рядка повертають результати у форматі структурованого JSON-документа.
5. **Визначення ролей та політик (Azure RBAC & Azure Policy):** Набори прав доступу, операції `Actions` та `NotActions` формалізуються у вигляді JSON-структур.

**<span>3. Які є види Azure API? Коротко опишіть їх.</span>** <br>
Хмарна платформа Microsoft Azure надає кілька спеціалізованих категорій програмних інтерфейсів API для взаємодії з різними рівнями інфраструктури:
1. **Azure Resource Manager (ARM) REST API (Control Plane APIs):**
   * *Призначення:* Керування життєвим циклом інфраструктурних ресурсів (створення, оновлення, моніторинг конфігурацій, масштабування та видалення віртуальних машин, мереж, баз даних, сховищ).
   * *Особливості:* Єдина точка входу до панелі управління Azure Management, авторизація через OAuth 2.0 токени Entra ID, підтримка механізмів аудиту та ролей Azure RBAC.
2. **Data Plane APIs (Сервісні API роботи з даними):**
   * *Призначення:* Безпосередня взаємодія з даними, збереженими всередині конкретного сервісу.
   * *Приклади:* Azure Blob Storage REST API (завантаження та зчитування файлів), Azure Cosmos DB SQL/MongoDB API (виконання транзакцій над базами даних), Azure Service Bus API (надсилання та вичитування повідомлень із черги).
3. **Microsoft Graph API:**
   * *Призначення:* Уніфікований корпоративний REST API для доступу до хмарних сутностей організації Microsoft.
   * *Особливості:* Дозволяє керувати користувачами, групами Entra ID, ліцензіями, політиками доступу, аудитом безпеки, а також сервісами Microsoft 365 через єдину точку доступу Graph API.
4. **Azure Management Libraries & SDKs:**
   * *Призначення:* Спеціалізовані типізовані клієнтські бібліотеки для популярних мов програмування (.NET/C#, Python, Java, JavaScript/TypeScript, Go).
   * *Особливості:* Інкапсулюють прямі HTTP REST-виклики у зручні об'єктно-орієнтовані методи, автоматично обробляючи автентифікацію, повторні спроби запитів (retries) та серіалізацію даних.

**<span>4. Як можна встановити Azure CLI під різними операційними системами?</span>** <br>
* **Microsoft Windows:**
  1. Завантаження та запуск стандартного графічного пакета MSI-інсталятора з офіційного сайту Microsoft;
  2. За допомогою системного диспетчера пакетів Windows Package Manager у консолі PowerShell:
     ```powershell
     winget install -e --id Microsoft.AzureCLI
     ```
  3. Через менеджер пакетів Chocolatey: `choco install azure-cli`.
* **Apple macOS:**
  Встановлення здійснюється через термінальний менеджер пакетів Homebrew за допомогою команд:
  ```bash
  brew update
  brew install azure-cli
  ```
* **Дистрибутиви GNU/Linux (Ubuntu / Debian):**
  1. Встановлення з офіційного репозиторію за допомогою системного менеджера пакунків APT:
     ```bash
     sudo apt-get update && sudo apt-get install azure-cli
     ```
  2. Оновлення та перевірка через термінал.
* **Універсальний запуск через Docker-контейнер:**
  Запуск ізольованого середовища з попередньо встановленим Azure CLI на будь-якій системі:
  ```bash
  docker run -it mcr/azure-cli
  ```

**<span>5. Розгляньте базові команди Azure CLI. Наведіть приклади.</span>** <br>
1. *Інтерактивна автентифікація в обліковому записі:*
   ```bash
   az login
   ```
2. *Перегляд активної підписки та її ідентифікаторів:*
   ```bash
   az account show --output table
   ```
3. *Створення нової групи ресурсів у західноєвропейському дата-центрі:*
   ```bash
   az group create --name RG-CloudServices-Lab6 --location westeurope
   ```
4. *Швидке створення віртуальної машини Ubuntu з автоматичною генерацією SSH-ключів:*
   ```bash
   az vm create --resource-group RG-CloudServices-Lab6 --name MyAzureVM --image Ubuntu2204 --admin-username azureuser --generate-ssh-keys
   ```
5. *Отримання табличного списку розгорнутих віртуальних машин:*
   ```bash
   az vm list --output table
   ```
6. *Створення облікового запису хмарного сховища Storage Account:*
   ```bash
   az storage account create --name mystoragelab2026 --resource-group RG-CloudServices-Lab6 --location westeurope --sku Standard_LRS
   ```
7. *Повне видалення групи ресурсів разом з усіма внутрішніми віртуальними серверами та дисками:*
   ```bash
   az group delete --name RG-CloudServices-Lab6 --yes --no-wait
   ```
