**2.1. Намалюйте діаграму, яка відображатиме архітектуру Docker.** <br>
Архітектура Docker побудована за клієнт-серверною моделлю (Client-Server Architecture), де клієнтський компонент Docker CLI взаємодіє з фоновим демоном Docker Daemon (dockerd) через REST API за допомогою UNIX-сокетів або мережевих TCP-з'єднань. Демон Docker Daemon відповідає за виконання важкої роботи з управління об'єктами хмари: будівництво образів (Images), запуск та ізоляцію контейнерів (Containers), налаштування віртуальних мереж (Networks) та підключення автономних дискових томів (Volumes). Управління дистрибутивом образів здійснюється через реєстр Docker Registry (наприклад, публічний Docker Hub), звідки демон завантажує необхідні шаровані файлові системи.

```
+-------------------------------------------------------------------+
|                           DOCKER HOST                             |
|                                                                   |
|   +------------------+         +------------------------------+   |
|   |   Docker CLI     |         |        Docker Daemon         |   |
|   | (Client Terminal)|         |          (dockerd)           |   |
|   +--------+---------+         +--------------+---------------+   |
|            |                                  |                   |
|            | REST API / UNIX Socket           |                   |
|            +--------------------------------->|                   |
|                                               |                   |
|   +-------------------------------------------+---------------+   |
|   |                                                           |   |
|   |  +-----------------+  +-----------------+  +-----------+  |   |
|   |  |   Containers    |  |     Images      |  |  Volumes  |  |   |
|   |  |  [Ubuntu/Apache]|  | [ubuntu:latest] |  |  & Nets   |  |   |
|   |  |  [Alpine/Nginx] |  | [nginx:alpine]  |  |           |  |   |
|   |  +-----------------+  +-----------------+  +-----------+  |   |
|   +-------------------------------------------+---------------+   |
+-----------------------------------------------+-------------------+
                                                ^
                                                | Pull / Push
                                                v
                                 +------------------------------+
                                 |       DOCKER REGISTRY        |
                                 |         (Docker Hub)         |
                                 +------------------------------+
```

**2.2. Чим відрізняється Docker-контейнер від Docker-образу?** <br>
Docker-образ (Image) є статичним шарованим шаблоном «тільки для читання» (Read-Only Template), який містить виконуваний код програми, мінімальне оточення операційної системи, системні бібліотеки, залежності та конфігураційні інструкції для запуску додатка. Натомість Docker-контейнер (Container) являє собою динамічний, за запущений ізольований екземпляр (Instance) образу, який додає над статичними шарами образу додатковий тонкий шар запису («Read-Write Layer» або Container Layer). Таким чином, образ можна порівняти з класом в об'єктно-орієнтованому програмуванні або інсталяційним дистрибутивом, тоді як контейнер є конкретним виконуваним об'єктом у оперативній пам'яті, який має власний стан, PID-простір, мережевий інтерфейс та файлову систему.

---

**2.3. Як можна подивитися список запущених контейнерів?** <br>
Для перегляду списку всіх активних (запущених у даний момент) контейнерів у командному рядку використовується фундаментальна команда `docker ps`. Якщо ж необхідно отримати вичерпну інформацію про абсолютно всі контейнери у системі, включаючи ті, що перебувають у зупиненому стані (Stopped/Exited) або завершили свою роботу з помилкою, застосовується команда з розширеним прапорцем `docker ps -a` (або `docker container ls -a`).

---

**2.4. Як передати локальний порт до контейнера?** <br>
Передача або прокидання локального порту хост-системи у внутрішню мережу контейнера здійснюється під час його запуску за допомогою прапорця `-p` (або `--publish`) у синтаксисі `docker run -p <Host_Port>:<Container_Port> <Image_Name>`. Наприклад, виконання команди `docker run -d -p 8080:80 nginx` зв'язує порт 8080 вашої фізичної або віртуальної хост-машини з внутрішнім портом 80 контейнера Nginx, що дозволяє звертатися до веб-сервера у браузері за адресою `http://localhost:8080`.

---

**2.5. Як можна зв'язати кілька контейнерів між собою?** <br>
Сучасним стандартом зв'язування та мережевої взаємодії кількох контейнерів у Docker є використання ізольованих користувацьких віртуальних мереж (User-Defined Bridge Networks), які створюються командою `docker network create <network_name>`, після чого контейнери приєднуються до цієї мережі за допомогою прапорця `--network` і можуть безперешкодно звертатися один до одного за власними іменами контейнерів завдяки вбудованому у Docker внутрішньому DNS-серверу. Для комплексних багатоконтейнерних додатків (наприклад, связки веб-сервера, бекенду та бази даних) застосовується інструмент оркестрації **Docker Compose**, де у декларативному файлі `docker-compose.yml` описуються всі сервіси, їхні мережеві зв'язки (services/networks) та спільні дискові томи.

### Відповіді на контрольні питання

**1. У чому полягає відмінність між docker stop і docker rm?** <br>
Головна відмінність між даними командами полягає у життєвому циклі та стані об'єкта контейнера: команда `docker stop` здійснює м'яке програмне вимкнення виконуваних процесів всередині контейнера (надсилаючи сигнал `SIGTERM`, а через таймаут `SIGKILL`), причому сам контейнер залишається збереженим на диску разом з усіма змінами у його файловій системі, конфігураціями та логами й може бути відновлений командою `docker start`, тоді як команда `docker rm` остаточно видаляє зупинений контейнер, його конфігураційний шар запису та внутрішні ідентифікатори з бази даних Docker Engine без можливості подальшого запуск.

---

**2. Які є альтернативи docker? Зробіть порівняння їх можливостей.** <br>
Сучасна екосистема контейнеризації пропонує декілька потужних альтернатив Docker, серед яких найпопулярнішим є **Podman** (демон-less інструмент від Red Hat, який підтримує сумісний CLI-синтаксис, працює за замовчуванням у безпривілейованому rootless-режимі та не вимагає центрального демона), **Containerd** (високопродуктивне середовище виконання контейнерів низького рівня, яке є стандартом де-факто у Kubernetes через CRI), **LXC/LXD** (технологія системної контейнеризації, яка ізолює повноцінні операційні системи замість окремих додатків), а також **CRI-O** (легковажний runtime, розроблений спеціально для інтеграції з Kubernetes), що дозволяє вибирати оптимальний інструмент залежно від вимог до безпеки, оркестрації та архітектури.

---

**3. Що таке rootless-контейнеризація? Наведіть приклади та пояснення до них.** <br>
Rootless-контейнеризація являє собою технологію запуску демона контейнеризації та самих контейнерів від імені звичайного непривілейованого користувача операційної системи (Non-Root User) без надання суперексклюзивних прав `root` або доступу до привілейованих сокетів. Реалізація цієї технології базується на використанні механізму системних просторів імен ядра Linux (Linux User Namespaces), де привілейований UID 0 всередині контейнера відображається на звичайний непривілейований UID (наприклад, UID 1000) на хост-машині, яскравими прикладами чого є режим **Podman Rootless Mode** та **Docker Rootless Mode** (`dockerd-rootless.sh`).

---

**4. Як впливає rootless-контейнеризація на безпеку?** <br>
Rootless-контейнеризація кардинально підвищує рівень кібербезпеки та ізоляції хмарних систем, оскільки вона усуває критичний вектор атак типу Container Escape (втеча з контейнера): у разі виявлення уразливості у веб-додатку або веб-сервері та компрометації контейнера, зловмисник, навіть здобувши права `root` всередині ізольованого середовища, на фізичній хост-системі залишається звичайним користувачем без системних привілеїв і не має можливості модифікувати ядро ОС, отримати доступ до мережевих інтерфейсів хоста чи пошкодити файлові системи інших користувачів.

---

**5. Яку роль відіграє контейнеризація в хмарних технологіях?** <br>
Контейнеризація є фундаментальним наріжним каменем сучасної хмарної архітектури (Cloud-Native Development), який забезпечує кросплатформену портованість додатків за принципом «напиши один раз — запускай де завгодно», дозволяючи пакувати код разом з усіма залежностями в єдиний стандартизований образ. Вона забезпечує високу щільність розміщення ресурсів, надшвидкий запуск мікросервісів за лічені мілісекунди, є основою для автоматизації конвеєрів безперервної інтеграції та доставки (CI/CD) і слугує базовим елементом для платформ оркестрації, таких як Kubernetes, Google Kubernetes Engine (GKE), Amazon ECS та Azure Kubernetes Service (AKS).

### Висновки

У ході виконання лабораторної роботи №10 було детально опановано теоретичні засади та практичні навички роботи з технологією контейнеризації Docker. Під час практичних завдань розгорнуто та досліджено інтерактивний контейнер на базі образу Ubuntu Linux із встановленням і кастомізацією веб-сервера Apache2, опрацьовано команди управління життєвим циклом контейнерів (`docker pull`, `docker run`, `docker ps -a`, `docker stop`, `docker rm`), а також реалізовано другу практичну ітерацію із застосуванням легковагового образу Alpine Linux та веб-сервера Nginx. Додатково проведено глибокий аналіз альтернативних середовищ виконання (Podman, Containerd), вивчено переваги використання rootless-контейнеризації для підвищення безпеки хмарних систем та зафіксовано ключову роль контейнерів у побудові сучасних Cloud-Native та мікросервісних архітектур.
