**1. В чому суть концепції Storage-as-a-Service, коли її доцільно використовувати?**

**STaaS (Storage-as-a-Service / Сховище як послуга)** - це модель надання дискового простору та сервісів збереження даних через інтернет за моделлю підписки або оплати за фактично використаний обсяг (Pay-as-you-go). Користувач позбавляється необхідності купувати
фізичні сервери зберігання (SAN/NAS), займатися їхнім обслуговуванням, заміною несправних дисків та реплікацією - усю апаратну інфраструктуру, стійкість до збоїв та масштабування забезпечує хмарний провайдер.  

Доцільно використовувати при непередбачуваному рості даних, коли бізнес не може спрогнозувати точний обсяг сховища на 1–3 роки вперед і потребує еластичного масштабування без капітальних витрат (CAPEX). Концепція є корисною
при збереженні медіаконтенту та бекапів для розміщення користувацьких файлів, статичного вебконтенту, дистрибутивів, архівів або вторинних копій баз даних. Також використовується для розподіленого доступу, коли необхідно надати
високошвидкісний захищений доступ до файлів користувачам або сервісам з усього світу.

| :--- | :--- | :--- |

**4. Опишіть для чого потрібні такі дії над бакетами як Versioning, Lifecycle та Replication.**

**Versioning (Версіонування)** - це механізм збереження кількох версій одного й того самого об'єкта в межах бакету. Дозволяє відновити випадково перезаписані або видалені файли (створює `Delete Marker` замість повного знищення), 
захищає від людських помилок та атак програм-вимагачів (Ransomware).  

**Lifecycle Policies (Політики життєвого циклу)** є набором автоматизованих правил для оптимізації витрат. Дозволяє автоматично переміщувати об'єкти між класами зберігання в міру їхнього старіння (наприклад, через 30 днів перенести 
з `S3 Standard` в `S3 Standard-IA`, через 90 днів - в архів `S3 Glacier`, а через 365 днів - остаточно видалити).  

**Replication (Реплікація)** - автоматичне асинхронне копіювання об'єктів між бакетами. Розрізняють *Cross-Region Replication (CRR)* - копіювання в інший географічний регіон для забезпечення Disaster Recovery (аварійного відновлення) та зменшення latency для користувачів на інших континентах,
а також *Same-Region Replication (SRR)* - копіювання в межах того самого регіону (наприклад, між production та test акаунтами для збереження резервних логів).

<br>

**5. Які методи захисту від несанкціонованого доступу до бакетів існують?**

1.  **S3 Block Public Access** - централізований перемикач безпеки на рівні акаунта або бакета, який блокує будь-які спроби зробити бакет або його об'єкти публічними.
2.  **Bucket Policies** - JSON-документи політик на рівні бакета, що детально регламентують, кому (Principal), з яких IP-адрес і які дії (`s3:GetObject`, `s3:PutObject`) дозволено або заборонено (`Allow` / `Deny`).
3.  **IAM Policies** - політики ідентичності, які призначаються користувачам, групам або ролям для надання прав на взаємодію з S3.
4.  **Access Control Lists (ACLs)** - застарілий механізм розмежування доступу на рівні окремих об'єктів або бакетів (AWS рекомендує вимикати ACL на користь Bucket Policies).
5.  **Шифрування даних (Encryption):**
    *   *SSE-S3* - шифрування ключами, керованими AWS.
    *   *SSE-KMS* - шифрування ключами через AWS Key Management Service з контролем аудиту.
    *   *SSE-C* - шифрування за допомогою ключів клієнта.
6.  **S3 Object Lock (WORM — Write Once, Read Many)** - блокування можливості перезапису або видалення об'єктів на фіксований термін (вимога регуляторів фінансової та медичної галузей).
7.  **Pre-signed URLs** - тимчасові згенеровані посилання з обмеженим терміном дії (наприклад, 15 хвилин) для безпечного завантаження або скачування конкретного файлу без відкриття публічного доступу до бакета.

</blockquote>

<blockquote>

**6. В чому суть концепції Function-as-a-Service (FaaS), коли її доцільно використовувати?**

**FaaS (Функція як послуга)** - це категорія хмарних обчислень, що дозволяє розробникам запускати окремі атомарні фрагменти коду (функції) у відповідь на події (Events) без необхідності розгортання, налаштування та підтримки серверів або контейнерних платформ. Обчислювальні ресурси виділяються динамічно в момент виклику функції та миттєво звільняються після її завершення. Оплата нараховується суто за час фактичного виконання (з точністю до мілісекунд) та обсяг використаної оперативної пам'яті.  

Доцільно використовувати при розв'язанні подійно-орієнтованих задач (Event-Driven) для обробки завантажених файлів на S3, реагування на записи в базі даних, прийом вебхуків (Webhooks). Використовується при нерівномірному / періодичному навантаженні з 
бекендом із піковими або рідкісними запитами (наприклад, cron-задачі, генерація щотижневих звітів), де звичайний сервер більшу частину часу простоював би. Також концепція має місце в мікросервісній архітектурі для розбиття бекенду на незалежні легко підтримувані функції, що зв'язуються через API Gateway.

<br>

**7. Опишіть поняття “Serverless-архітектури”.**

**Serverless (Безсерверна архітектура)** - це парадигма розробки програмного забезпечення, за якої розробник повністю абстрагується від управління інфраструктурою (серверами, ОС, патчами, масштабуванням). 
Фізичні або віртуальні сервери все одно існують, але всі обов'язки щодо їхнього адміністрування, моніторингу, високої доступності та автоматичного горизонтального масштабування перекладені на хмарного провайдера.
До ключових рис Serverless належить відсутність потреби в адмініструванні серверів, автоматичне масштабування від 0 до тисяч паралельних екземплярів, нульова вартість у стані спокою (No Idle Costs) та вбудована відмовостійкість.

<br>

**8. Порівняйте поняття serverless-архітектури та Function-as-a-Service (FaaS).**

FaaS є **підмножиною** ширшої концепції Serverless. Різниця полягає в тому, що *FaaS* стосується виключно **обчислювального рівня (Compute Layer)** - виконання самого програмного коду (наприклад, AWS Lambda, Google Cloud Functions), тоді як 
*Serverless Architecture* охоплює **всю екосистему застосунку**, включно зі сховищами (Amazon S3), безсерверними базами даних (Amazon DynamoDB, Aurora Serverless), чергами повідомлень (Amazon SQS), шинами подій (Amazon EventBridge) та шлюзами API (Amazon API Gateway). 
Повноцінний serverless-додаток будується з FaaS-функцій та інших serverless-сервісів.

<br>

3.  Створити функцію AWS Lambda, підключити створену IAM Role та розмістити код обробки зображень.
4.  У налаштуваннях Lambda (Add Trigger) вказати Amazon S3, обрати вихідний бакет і подію створення файлів.
5.  Протестувати завантаження зображення та перевірити появу мініатюри в цільовому бакеті.

<blockquote>

**11. Опишіть можливості Amazon RDS (Relational Database Service). До якої хмарної моделі її можна віднести?**

Щодо можливостей Amazon RDS, це повністю керована служба реляційних баз даних, яка бере на себе рутинні завдання адміністрування, а саме: встановлення та конфігурацію СУБД, автоматичне застосування оновлень безпеки (patching), щоденне створення резервних копій 
(automated backups), відновлення стану на будь-яку секунду (Point-in-Time Recovery), автоматичне перемикання при аваріях (Multi-AZ Failover), вертикальне та горизонтальне масштабування (Read Replicas).  

Відноситься до моделі **PaaS (Platform as a Service)** або спеціалізованої підкатегорії **DBaaS (Database-as-a-Service)**. Користувач не має доступу до операційної системи хоста, але повністю керує схемою даних, індексами, користувачами БД та SQL-запитами.

<br>

**12. Які бази даних підтримує Amazon RDS. Порівняйте їх за можливостями.**

1.  **Amazon Aurora** - власна хмарна СУБД від AWS, повністю сумісна з MySQL та PostgreSQL. Працює до 5 разів швидше за стандартний MySQL, має розподілене самовідновлюване сховище на 6 копій у 3 зонах доступності та підтримку serverless-режиму (Aurora Serverless).
2.  **PostgreSQL** - потужна об'єктно-реляційна open-source СУБД. Відмінна підтримка складних аналітичних запитів, типів даних JSON/JSONB, геопросторових даних (PostGIS).
3.  **MySQL** - найпопулярніша open-source реляційна база даних для вебдодатків (WordPress, e-commerce). Висока швидкість читання, простота адміністрування.
4.  **MariaDB** - покращений форк MySQL, створений первинними розробниками MySQL. Підтримує оптимізовані рушії зберігання даних (Aria, ColumnStore).
5.  **Oracle Database** - комерційна корпоративна СУБД із підтримкою складних бізнес-транзакцій (Enterprise OLTP). Підтримує моделі ліцензування «Bring-Your-Own-License» (BYOL) та «License Included».
6.  **Microsoft SQL Server** - комерційна СУБД від Microsoft із глибокою інтеграцією в стек .NET та екосистему Windows Server.

**13. Порівняйте процес розгортання БД на базі Amazon RDS (PaaS-модель) та EC2 + MySQL (або інша БД) вручну (IaaS-модель). Коли доцільно використовувати їх?**

| Параметр порівняння | Amazon RDS (PaaS / DBaaS) | Self-Hosted на Amazon EC2 (IaaS) |
| :--- | :--- | :--- |
| **Час розгортання** | 5–10 хвилин через кілька кліків або API. | Кілька годин (створення ВМ, налаштування OS, інсталяція СУБД, конфігурація). |
| **Оновлення та патчі** | Автоматичні у вказані сервісні вікна (Automated Patching). | Повністю ручне встановлення оновлень ядра ОС та пакетів СУБД адміністратором. |
| **Резервне копіювання** | Автоматичне з можливістю Point-in-Time Restore. | Необхідно самостійно писати cron-скрипти, робити дамп та копіювати на S3. |
| **Висока доступність (HA)** | Вмикається одним прапорцем Multi-AZ (синхронна реплікація). | Складне ручне проектування кластера, налаштування реплікації та failover-скриптів. |
| **Доступ до ОС хоста** | Заблокований (немає доступу по SSH/RDP до сервера). | Повний Root-доступ до терміналу та конфігураційних файлів ОС. |
| **Коли використовувати** | Стандартні комерційні проєкти, фокус на швидкість та стабільність. | Необхідність кастомних плагінів СУБД, нестандартних версій або специфічних налаштувань ОС. |

**14. Опишіть для чого потрібні операції масштабування, створення снепшотів, моніторингу та логування баз даних.**

**Масштабування (Scaling)** буває декількох видів:
* *Вертикальне (Vertical Scaling)* - зміна типу інстансу (збільшення vCPU та RAM) або розширення обсягу диска без простою при зростанні бази.
* *Горизонтальне (Horizontal Scaling / Read Replicas)* - створення 
копій бази тільки для читання для розвантаження основного master-вузла під час напливу клієнтів.

**Створення снепшотів (DB Snapshots)** - ручні точкові резервні копії всього екземпляра БД, які безстроково зберігаються на S3. Необхідні перед накатуванням великих міграцій коду або релізів.

**Моніторинг (Monitoring)** - збір метрик навантаження через Amazon CloudWatch (використання CPU, вільної пам'яті, IOPS, кількості з'єднань) для виявлення вузьких місць у продуктивності.

**Логування (Logging)** - запис журналів повільних запитів (Slow Query Log), помилок (Error Log) та журналу загальних подій у CloudWatch Logs для оптимізації SQL-запитів та розслідування інцидентів безпеки.

<br>

**15. Порівняйте поняття реляційних та NoSQL баз даних. Чи підтримує NoSQL сервіс Amazon RDS?**

**Реляційні БД (SQL / RDBMS)** зберігають дані у суворо структурованих таблицях із рядками та стовпцями. Підтримують зовнішні ключі (Foreign Keys), схему (Schema-on-Write) та транзакційні гарантії ACID (Atomicity, Consistency, Isolation, Durability). 
Приклади: PostgreSQL, MySQL, Oracle.  

**NoSQL БД** - нереляційні сховища з гнучкою динамічною схемою (Schema-on-Read). Оптимізовані під горизонтальне масштабування, роботу з гігантськими обсягами неструктурованих даних та ультранизьку затримку (Single-digit millisecond latency). Моделі: Key-Value, Document, Column, Graph.
Щодо підтримки NoSQL у сервісі Amazon RDS, її немає. Класичний Amazon RDS призначений суто для реляційних баз даних. Хоча сучасні PostgreSQL та MySQL в RDS вміють зберігати атрибути у форматі JSON/JSONB, для повноцінної NoSQL-роботи в екосистемі AWS використовуються окремі профільні сервіси: Amazon DynamoDB (Key-Value/Document), Amazon DocumentDB (MongoDB-сумісна) та Amazon Keyspaces (Cassandra-сумісна).

</blockquote>

**16. Наведіть класифікацію сучасних NoSQL баз даних. Де вони використовуються в хмарних технологіях?**

1.  **Ключ-значення (Key-Value Stores).** Дані зберігаються як пари унікального ключа та асоційованого значення. Найшвидший пошук за ключем. Приклади: *Amazon DynamoDB, Redis, Memcached*. (Використання: сесії користувачів, кешування, кошики інтернет-магазинів).
2.  **Документні (Document Stores).** Дані зберігаються у вигляді напівструктурованих документів (JSON, BSON, XML). Приклади: *Amazon DocumentDB, MongoDB, Couchbase*. (Використання: каталоги товарів, профілі користувачів, системи управління контентом CMS).
3.  **Колонкові (Wide-Column Stores).** Дані зберігаються за родинами колонок, оптимізовані під швидкий запис і читання розріджених даних. Приклади: *Amazon Keyspaces, Apache Cassandra, HBase*. (Використання: телеметрія IoT, фінансові часові ряди, аналітика логів).
4.  **Графові (Graph Databases).** Зберігають дані у вигляді вузлів (Nodes) та ребер (Edges) для представлення зв'язків. Приклади: *Amazon Neptune, Neo4j*. (Використання: соціальні мережі, рекомендаційні системи, аналіз шахрайства).

<br>

**17. Опишіть можливості та застосування Amazon DynamoDB.**  

Це повністю керована безсерверна NoSQL-база даних класу Key-Value та Document, що забезпечує стабільну затримку до 10 мілісекунд при будь-якому масштабі навантаження. Основні характеристики включають автоматичне партиціювання та масштабування від кількох запитів до мільйонів на секунду, вбудовану реплікацію даних між 3 зонами доступності, підтримку шифрування, автоматичне очищення застарілих записів через TTL (Time to Live), 
підтримку глобальних таблиць (Global Tables) із мультирегіональним записом. Застосувують для збереження ігрових сесій та таблиць лідерів, корзини покупців в e-commerce, мобільні додатки з високим трафіком, трекінг замовлень у реальному часі.

<br>

**18. Опишіть основні поняття Amazon DynamoDB: Primary Key, WCU та RCU.**

**Primary Key (Первинний ключ)** - унікальний ідентифікатор кожного елемента (Item) в таблиці:
*   *Partition Key (Simple Key)* - одноатрибутний ключ. Його значення хешується для визначення фізичної партиції, де зберігається запис.
*   *Composite Primary Key (Partition Key + Sort Key)* - складений ключ. Partition Key визначає фізичну партицію, а Sort Key впорядковує дані всередині цієї партиції (дозволяє робити вибірки за діапазонами значень).
  
**RCU (Read Capacity Unit)** - одиниця пропускної здатності читання. 1 RCU надає можливість виконати одне суворо узгоджене читання (Strongly Consistent Read) або два узгоджених у кінцевому підсумку читання (Eventually Consistent Read) на секунду для запису розміром до 4 КБ.

**WCU (Write Capacity Unit)** - одиниця пропускної здатності запису. 1 WCU надає можливість записати один елемент розміром до 1 КБ на секунду.

<br>

**19. Порівняйте сервіси AWS для роботи з NoSQL базами даних - Amazon DynamoDB, Amazon DocumentDB та Amazon Keyspaces**

| Критерій | Amazon DynamoDB | Amazon DocumentDB | Amazon Keyspaces |
| :--- | :--- | :--- | :--- |
| **Модель даних** | Key-Value та Document. | Документна (Document / BSON). | Колонкова (Wide-Column). |
| **Сумісність з open-source** | Власний пропрієтарний API AWS. | Сумісна з Apache MongoDB API. | Сумісна з Apache Cassandra (CQL API). |
| **Архітектура інфраструктури**| Повністю безсерверна (Serverless). | Кластерна (екземпляри інстансів + розподілене сховище). | Безсерверна (Serverless Cassandra). |
| **Масштабування пропускної здатності** | On-Demand (автоматично) або налаштовані RCU/WCU. | Вертикальне масштабування інстансів + Read Replicas. | Автоматичне виділення місткості за запитами (On-Demand). |
| **Головні кейси** | Ультрашвидкі мобільні та вебсервіси, мікросервіси. | Міграція існуючих додатків із MongoDB у хмару AWS. | Обробка величезних потоків телеметрії IoT та часових рядів. |

**20. Наведіть приклади ІТ-задач, де буде доцільно використовувати Amazon DynamoDB, Amazon DocumentDB та Amazon Keyspaces. Як їх розгорнути в AWS?**

**Amazon DynamoDB:**
*   *Задача:* Облік стану тренувань користувачів та збереження GPS-координат мобільного застосунку FitPulse App.
*   *Як розгорнути в AWS:* Зайти в консоль DynamoDB -> натиснути **Create table** -> ввести назву таблиці `UserWorkouts` -> вказати Partition Key `user_id` (String) та Sort Key `timestamp` (Number) -> обрати режим виділення ресурсів **On-Demand** ->
  натиснути **Create table**.

**Amazon DocumentDB:**
*   *Задача:* Каталог товарів маркетплейсу зі складною змінною структурою атрибутів (одяг, електроніка, автозапчастини), який мігрує з MongoDB.
*   *Як розгорнути в AWS:* Перейти у сервіс DocumentDB -> натиснути **Create cluster** -> обрати тип інстансу (наприклад, `db.t3.medium`) -> вказати ідентифікатор кластера та облікові дані адміністратора -> налаштувати VPC та Security Group ->
  підключитися через стандартний клієнт `mongosh`.

**Amazon Keyspaces:**
*   *Задача:* Збір показників датчиків температури та вібрації виробничого обладнання (IoT sensor metrics) із частотою сотні тисяч записів на секунду.
*   *Як розгорнути в AWS:* Перейти у сервіс Amazon Keyspaces -> створити простір ключів (Keyspace) `IoTSensors` -> усередині простору натиснути **Create table** -> визначити колонки за допомогою синтаксису Cassandra CQL та зберегти.

</blockquote>
